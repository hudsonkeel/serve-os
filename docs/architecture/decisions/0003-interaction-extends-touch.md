# ADR 0003 — Interaction Extends Touch In Place

**Status:** Accepted
**Date:** 2026-07-18
**Branch:** `feature/relationship-intelligence-interaction-capture`

## Context

Relationship Intelligence Phase 1 introduces a unified **Interaction** concept — one capture flow that replaces "Log Touch" as the primary relationship-history action. The scope requires a decision on whether Interaction *replaces*, *extends*, or *wraps* the existing `relationship_touches` table, and requires this to be recorded as an ADR since it materially affects the data model.

## Options considered

1. **Extend `relationship_touches` in place** — add the new columns Interaction needs (`interaction_result`, `participants`), extend `touch_type`'s allowed values, keep the table and RPC names.
2. **Replace with a new `relationship_interactions` table**, backfilling existing Touch rows into it, eventually retiring `relationship_touches`.
3. **New table for new rows only**, merged with the old table at the read layer (a view or an application-level union), leaving old Touches where they are permanently.

## Decision

**Option 1 — extend in place.**

- `relationship_touches` gains `interaction_result text` (nullable — legacy rows have none) and `participants jsonb not null default '[]'`, and its `touch_type` check constraint gains two new values (`internal_discussion`, `community_interaction`) without removing the existing ones (`assessment`, `proposal` are kept, unused by the new UI but not invalidated).
- The RPC and table names keep their `touch`-rooted names (`relationship_touches`, `log_relationship_touch` for the legacy lightweight path, plus the new `log_relationship_interaction` for the full workflow). Every user-facing surface says "Interaction" / "Log Interaction"; nothing in the schema does, and that's an intentional, revisitable naming decision — not a functional gap.

## Rationale

- **Zero backfill.** Every existing Touch row is already a valid Interaction the moment the new columns exist as nullable/defaulted — no migration pass over historical data, no risk to "production-like prototype data" the scope explicitly says to preserve.
- **Zero risk to the Action Board's existing quick-touch path**, which continues calling the original `log_relationship_touch` RPC unchanged (see the "Minimization decisions" section of the implementation plan — the Action Board's quick form was deliberately not upgraded to the full Insights/Commitments/Open Loops/Next-Action workflow).
- **The actual schema delta is small.** One nullable enum column, one jsonb column, two new enum values. A full table replacement would carry real migration risk for a change this size, which is directly against the scope's own "select the least disruptive architecture" instruction.
- Option 3 (new table, read-layer merge) was rejected because it leaves two tables to maintain indefinitely with a permanent union-query cost, for no benefit over Option 1 given how small the actual schema delta is.

## Consequences

- A future, purely cosmetic rename of `relationship_touches` → `relationship_interactions` (and the matching RPC/column names) remains available if ever wanted, entirely independent of this decision — nothing here forecloses it, and nothing here requires it.
- `relationship_actions` gained one new nullable FK column (`source_interaction_id`) so a Next Action can trace back to the Interaction that spawned it — additive, no existing behavior changed. (`source_commitment_id`/`source_open_loop_id` were proposed in the first draft and removed in the Revision below.)
- `relationship_timeline`'s `event_type` check constraint gained three new values (`interaction_logged`, `commitment_resolved`, `open_loop_resolved`); the existing `touch_logged` value is unchanged and still used by the legacy quick-touch path. (The first draft also added `insight_recorded`/`commitment_created`/`open_loop_created` — removed in the Revision below.)
- Working Note categories were reviewed per the scope's request but deliberately **not** changed in this migration — see the implementation doc's "Working Note categories" section. Retyping real prototype data's categories is a content decision, not a schema one, and is flagged as a Phase 2 follow-up rather than guessed at here. Working Notes did, however, gain new additive fields — see the Revision below (point 13).

## Revision (pre-commit review)

The migration below was reviewed in full before its first commit. Nothing in this section reverses the Decision above (Interaction still extends Touch in place; Insights/Commitments/Open Loops remain separate tables; `log_relationship_interaction` remains one atomic RPC; `participants` remains jsonb; everything remains additive). Thirteen points were raised; each is addressed here.

1. **Bidirectional lifecycle constraints.** The first draft's closure-metadata checks only verified one direction (e.g. "active requires no resolved_at/resolved_by") and silently allowed a resolved/outdated row with *no* closure metadata at all. All three lifecycle tables (`relationship_insights`, `relationship_commitments`, `relationship_open_loops`) now have bidirectional constraints: the open/active state requires null closure fields, and every terminal state requires them populated.
2. **Consistent closure audit fields.** `relationship_commitments` gained `closed_by` (was missing entirely) and its `completed_at`/`completion_note` were renamed to generic `closed_at`/`closure_note`, used for either terminal status (`status` itself distinguishes completed vs. cancelled). `relationship_open_loops` gained `resolved_by` (was missing). `relationship_insights` already had `resolved_by`.
3. **`superseded` deferred.** Removed from both Commitments' and Open Loops' status vocabularies — no RPC in this migration ever produced it (dead schema surface in the first draft), and no real supersede workflow (linking a record to what replaces it) exists yet to justify keeping it.
4. **Timeline noise reduced.** `insight_recorded`/`commitment_created`/`open_loop_created` are no longer produced or accepted — one `interaction_logged` event per submission already covers initial capture, with its `event_description` now summarizing how many of each were captured. `commitment_resolved`/`open_loop_resolved` still fire, only when something is later closed.
5. **`last_meaningful_touch_at` made conditional.** `log_relationship_interaction` now only advances it when `interaction_result` indicates real engagement — `left_voicemail` and `no_response` no longer count, matching the field's own name. (The pre-existing `log_relationship_touch` RPC, used only by the Action Board's lightweight quick-touch path, is untouched — it has no `interaction_result` concept at all.)
6. **Idempotency added.** `relationship_touches` gained a nullable, uniquely-indexed `idempotency_key`. `log_relationship_interaction` takes an optional `p_idempotency_key`; a retried/double-clicked submission with the same key returns the original row instead of duplicating it and its child records. The Log Interaction form generates one key per form session (`crypto.randomUUID()`), regenerated on reset.
7. **Input validation strengthened.** `p_touch_type`/`p_summary` are explicitly checked for null/blank (previously relied on the table's own `not null`/check constraints, which produce a generic Postgres error rather than a clear one). `p_participants`/`p_insights`/`p_commitments`/`p_open_loops` are each checked with `jsonb_typeof(...) = 'array'` before `jsonb_array_elements` is ever called — a non-array input now raises a clear exception instead of a cryptic Postgres error from the array function itself.
8. **Participant shape validated at the RPC boundary.** Each participant object is checked for a non-blank `name` and `role` before insertion — defense in depth alongside the existing TypeScript-level `validateParticipants` (`lib/relationships/validation.ts`), for any future caller that bypasses the application layer.
9. **Source-provenance deletion policy documented.** No RPC in this codebase ever deletes a `relationship_touches` row. `source_interaction_id` on all three new tables deliberately has **no** `on delete set null`/`on delete cascade` clause (defaults to `NO ACTION`) — if a hard-delete path for Interactions is ever added, it cannot silently orphan an Insight/Commitment/Open Loop's provenance; the delete itself would be blocked until that's explicitly designed. Deleting a Relationship still cascades everything beneath it, unchanged.
10. **`updated_at`/`updated_by` added** to `relationship_insights`, `relationship_commitments`, and `relationship_open_loops` (via a per-table trigger, matching this codebase's existing `*_set_updated_at` convention), so a future staleness-detection mechanism has something to compare against.
11. **`source_commitment_id`/`source_open_loop_id` deferred.** The first draft added both to `relationship_actions` speculatively — nothing in this phase ever sets them (only `source_interaction_id` is ever populated, via the Next Action composed inside `log_relationship_interaction`). Removed until a real workflow creates an Action directly from a Commitment or Open Loop.
12. **Relationship Brief persistence reconsidered, decision unchanged.** The Brief remains derived and non-authoritative, computed on-demand and never persisted in Phase 1 (see the implementation doc). Point 10's `updated_at` additions are exactly what a future persisted/staleness-tracked version would need (a per-source-table "last changed" signal to fingerprint against) — added now so that future work doesn't require another migration, without building the persistence itself.
13. **Working Note fields the original scope asked for, missed in the first draft.** The scope explicitly asked Working Notes to support "an optional expiration or review date, source description, linked resident, linked contact" — none of which the first draft added (it only reviewed, and deliberately left unchanged, the *category* vocabulary). Added: `relevant_until date`, `resident_id uuid` (real FK, `on delete set null`), `contact_name text`, `source_description text` (free text, not a formal Interaction FK — Working Notes are specifically for information that did *not* arise from a formal Interaction). The existing `open`/`resolved`/`archived` status vocabulary is kept as-is rather than renamed to the scope's literal "active/resolved/outdated" wording — treated as the same concept under this codebase's already-established names, since renaming a working, already-populated status column is the same kind of content decision the category-vocabulary review already declined to make.

## Upgrade compatibility (pre-commit review, second pass)

Running this migration against the shared Supabase project failed with Postgres error `42P13` ("cannot change name of input parameter `p_completion_note`", hinting to drop `resolve_relationship_commitment(uuid,text,text,text)` first). Investigation confirmed the true first draft of this migration (the one actually verified live, 12/12 checks passing, before the Revision above) had already been applied to the shared project — but a later working-tree revision, including the completion→closure rename and the `resolve_relationship_insight`/`resolve_relationship_commitment`/`resolve_relationship_open_loop` functions, had also reached the shared database out of band, using the pre-rename `p_completion_note` parameter name and a global (non-composite) idempotency index. The migration as written did not account for a database already carrying that intermediate shape — `CREATE TABLE IF NOT EXISTS` silently no-ops against a table that already exists, and `CREATE OR REPLACE FUNCTION` cannot rename an existing parameter even when every type in the signature is unchanged.

The migration is now written to apply cleanly to **both** a clean database and the shared database in its current state, as one transaction, with no separate patch file:

- **Functions**: `log_relationship_interaction` (old 14-parameter signature, before `p_idempotency_key` was added — a different parameter count is a different signature, so `CREATE OR REPLACE` would have created a second overload rather than replacing it), `resolve_relationship_insight`, `resolve_relationship_commitment` (the confirmed cause — old parameter name `p_completion_note`), and `resolve_relationship_open_loop` each get an explicit `drop function if exists public.<name>(<old argument types>)` immediately before their `create or replace function`. The insight/open-loop drops are defensive — applied on the same reasoning as the confirmed commitment case, since these three functions were added together in the same later revision.
- **Index**: `relationship_touches_idempotency_key_idx` (an earlier global unique index on `idempotency_key` alone) is dropped explicitly before creating the final composite `relationship_touches_relationship_idempotency_key_idx` on `(relationship_id, idempotency_key)`.
- **Columns**: `relationship_commitments.completion_note`/`completed_at` are renamed to `closure_note`/`closed_at` only if the old names are still present (a guarded `do $$ ... $$` block checking `information_schema.columns`, so a fresh install — which never has the old names — is unaffected); `closed_by`/`updated_by`/`updated_at` (insights, commitments, open loops) and `resolved_by` (open loops) are added via `add column if not exists`. `relationship_actions.source_commitment_id`/`source_open_loop_id` — the speculative columns removed in point 11 above — are dropped if present.
- **Constraints**: every lifecycle check that changed shape (`relationship_commitments_status_check`, `relationship_commitments_closure_fields_check` — plus an explicit drop of the old `relationship_commitments_completion_fields_check`, which is never redefined under that name in the final schema and would otherwise remain in force — `relationship_open_loops_status_check`, `relationship_open_loops_resolved_fields_check`, `relationship_insights_resolved_fields_check`) is dropped and re-added by name. All three new tables' `source_interaction_id` foreign keys are dropped and re-added without `on delete set null`, matching point 9's provenance-protection decision, using Postgres's default `<table>_<column>_fkey` constraint name.
- **Data normalization**: none required. `relationship_insights`, `relationship_commitments`, and `relationship_open_loops` are confirmed empty in the shared project — every synthetic Phase 1 demo row was removed in the prior cleanup pass — so narrowing the status vocabulary and tightening the bidirectional checks cannot reject any existing row, and the column renames move zero rows of data.
- **Triggers**: already upgrade-safe as originally written (`drop trigger if exists set_updated_at on <table>` precedes every `create trigger`) — no change needed.
- **Grants**: unaffected — every `revoke`/`grant execute` in this migration already runs immediately after its function's `create or replace`, which still executes normally after the new `drop function if exists` statements.
- **TypeScript callers**: confirmed already using the final parameter names (`lib/data/relationships.ts`'s `resolveRelationshipCommitment` sends `p_closure_note`, not `p_completion_note`) — no application-layer change was needed.

This remains one migration, one transaction (`begin` / `commit`), not a separate manual patch — every `drop ... if exists` is a no-op on a clean database and a real fix against the shared database's current state, so the same file is authoritative for both.
